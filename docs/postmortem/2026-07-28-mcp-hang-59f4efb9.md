# MCP hang investigation — thread `59f4efb9`

Date: 2026-07-28  
Thread: [59f4efb9](59f4efb9-f20e-4937-8d43-bff463c137ff) (legadoSkill agent transcript)  
Scope: phone MCP (Legado App) + PC `source-cli` / serial repair

## Verdict

The ~11 hour “stop” was not a deliberate pause. A **phone MCP tool call stopped returning**, the **serial batch never wrote a finish marker**, and the **agent stayed on a long `AwaitShell`** with no heartbeat watchdog. Three layers failed open.

## What happened (timeline)

1. Serial batch 3 started ~12:13 local; last useful log ~12:20 (after `hunt_empty` → `prep` → `cooldown 3s`).
2. No further `REPORT_JSON` / `serial_*_last.json` finish fields → stuck inside the next phone MCP step (`get_source` / `debug_source` / verify).
3. Agent waited on shell completion; wall clock accumulated ~10.9h until the user asked for status.

## Failure stack (evidence-backed)

| Layer | Failure | Evidence |
|-------|---------|----------|
| **Phone MCP** | In-flight tool call did not complete (or TCP stayed half-open) | Batch froze mid-URL with no REPORT; process later gone while terminal still “running” |
| **PC channel lock** | Windows `pid_alive` always true → dead PID locks waited **6h** TTL | Fixed in legadoSkill `source-mcp` (`channel_pid` + shorter stale) |
| **PC serial** | In-process oneshot: one hung MCP blocked the whole batch | Fixed: subprocess + `--url-timeout-s` (default 120) + heartbeat files |
| **Agent ops** | Long `AwaitShell` on whole batch; no poll of `serial_heartbeat.json` | Discipline §19–20 + SKILL traps added in Skill repo |

## Other MCP / Legado issues found in that thread (not only the hang)

## Root-cause hypotheses (ranked)

1. **Most likely:** phone-side long tool call + **engine restart on Wi‑Fi churn** or **non-returning streamable-HTTP session**, so PC ureq waited until process/TCP died.
2. **Likely:** hung `debug_source` / verify path where cancellation did not surface to the HTTP response (client waited; serial had no wall-clock kill yet).
3. **Amplifier only:** Windows zombie channel lock + agent AwaitShell (made a minutes-long hang into hours of idle).

## App changes shipped with this postmortem

1. `GET /mcp/health` — liveness + `busy` / `stale` / last tool timestamps (token required).
2. Defer `upMcpServer()` while debug/check busy (network churn **and** start/restart intents); apply when idle.
3. Watchdog tick (~3 min): restore service + **force-release stale** debug/check channels.
4. Align `debug_source` default `timeoutSec` to **90**; CIO `connectionIdleTimeoutSeconds=180`.
5. MCP tool `reset_mcp_channel` for emergency unlock (also unlocks `debugMutex`).
6. Check snapshot includes `lastProgressAt`; watchdog cancel waits for job `finally` before clearing busy mirrors.
7. Finish autorestart / NSD / lifecycle receivers already in the working tree.

Review follow-up (same commit): do not mark check idle before job `finally`; always `maybeNotifyIdle` after stale release; never drop `pendingNetworkRestart` on force-reset.
